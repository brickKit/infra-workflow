## 2. 功能详解

- **claim-first 幂等统一走 `command_idempotency` 一张表**（`repo/idempotency.go`），`CreateTask`/`CloseTask`/`CancelTask` 三个写命令共用同一套 `claimIdempotency`（INSERT ... ON CONFLICT DO NOTHING）→ 真正的写 → `finalizeIdempotency` 流程——**`workflow_tasks` 本身不重复存 `idempotency_key`**，那不是待办这个资源的持久属性，只是命令的输入回执（同 `erp-inventory` 的既有先例，第一版曾经设计成给 `workflow_tasks` 单独加一列，核对 `erp-inventory` 真实实现后改正）。
- **四个状态流转动作共用同一个核心 `transitionTaskTx`**（`repo/actions.go`）：锁行（`FOR UPDATE`）→ 校验仍是 `PENDING` → 更新状态 → 记一条 `workflow_task_actions`。**统一策略：不管走哪个入口，对一个已经不是 `PENDING` 的待办再次操作都返回 `ErrNotPending`**，不做"静默忽略"——claim-first 已经在更上一层保证了"同一个 `idempotency_key` 重放"不会走到这里；真的走到这里却状态不对，说明调用方拿错了 `task_id` 或者有并发的另一个动作抢先了，两种情况都值得报错。
- **`CloseTask`/`CancelTask` 的 `task_id` 是必填的，不是"二选一"**——这是设计过程中纠正过的一个判断：`GetTaskStatus` 的"按 `task_id` 或 `idempotency_key` 二选一"解决的是"超时时连 `task_id` 都没拿到"这个问题；`CloseTask`/`CancelTask` 的调用方从一开始就持有 `CreateTask` 返回的 `task_id`（同 `erp-inventory` `CancelReservation` 的既有判据：调用方存着 `reservation_id`，`idempotency_key` 只管这一次撤销命令本身的幂等，不用来反查该关哪个资源）。
- **`buf lint` 的 `RPC_REQUEST_RESPONSE_UNIQUE` 类规则**：同一个消息类型不能被多个 rpc 当返回值用。`CreateTask` 占了"读接口直接返回聚合根本身"（`Task`）这个名额，`CloseTask`/`CancelTask` 因此各自包一层 `CloseTaskResponse`/`CancelTaskResponse`——这是本项目第一次真正触发这条 STANDARD 规则（核对 `infra-authz` 的契约确认它从未复用过消息，此前从未被测试过）。
- **`ListTasks` 的 gRPC 面与 REST 面是两套完全不同的过滤逻辑**：gRPC `WorkflowService.ListTasks` 是组件间协议，本项目目前没有任何组件在 gRPC 侧转发/验证 JWT，因此不做数据权限过滤（同 `BatchGetTasks`/`GetTaskStatus`）；REST 的 `service.ListMyTasks`/`service.ListTasksAdmin` 才是数据权限真正生效的地方，各自从 `besdk.ScopeOf(ctx)` 取值。**这条边界曾经在 `.proto` 的注释里写错**（最初写成"走 ScopeFilter，从已验签的 JWT claims 推导"），核对全项目没有任何组件在 gRPC 层做过这件事之后改正。
- **"我的待办"（`GET /tasks`）用 OR，不是 AND 或"二选一 toggle"**——`assignee_sub = ScopeOwner` 或 `assignee_dept_path` 前缀命中 `ScopePrefix` 任一为真都该出现（契约明文）。**这条在实现中间纠正过一次真实 bug**：最初照抄 `erp-sales.ListOrders` 的 `ViewMine` toggle 写法（"我的"与"团队的"是互斥的两个视图），但如果只置 `ScopeOwner` 而把 `ScopePrefix` 留空，SQL 里 `dept_path LIKE '' || '%'` 会退化成匹配全部——OR 的两个操作数必须都从 `ScopeOf(ctx)` 真实派生，缺一个都是安全漏洞，不是"看少了"。`GET /admin/tasks` 才是真正的 toggle（`AdminView=true` 时只判 `ScopePrefix`，不判 `ScopeOwner`，外加可选的 `AssigneeSub` 精确过滤）。
- **approve/reject 要求当事人本人**（`service.actorInScope`）：与 `GetTaskDetail` 的 `Task.InScope`（OR，部门主管也能看见）是两条不同的判据——"看得见"不等于"能替他做决定"，"转办"是设计计划明确列出的未做功能，本阶段严格要求 `assignee_sub == 调用者自己`。
- **超期扫描是独立的后台循环，绝不修改 `status`**（`repo/overdue.go` + `module.go` 的 `startOverdueScan`）：每分钟扫一批 `due_at` 已过、仍是 `PENDING`、还没发过超期事件的待办，标记 `overdue_notified_at` 并发 `task.overdue.v1`——一批最多处理 100 条，处理满说明可能没扫完，立刻再跑一轮追上而不是等下一个 tick。

## 3. 完整契约清单

**gRPC `infra.workflow.v1.WorkflowService`**（6 个 rpc，见 `contracts/infra/workflow/v1/workflow.proto`）：

| rpc | 类型 | 幂等键 | 说明 |
|---|---|---|---|
| `CreateTask` | 命令 | ✅ `idempotency_key` | 登记待办 |
| `CloseTask` | 命令 | ✅ `idempotency_key` | 业务组件主动关闭（`exception` 修好了） |
| `CancelTask` | 命令 | ✅ `idempotency_key` | 来源单据作废，待办跟着作废 |
| `GetTaskStatus` | 读 | — | ⭐ 支持按 `idempotency_key` 查，不只按 `task_id` |
| `BatchGetTasks` | 读 | — | 防 N+1 |
| `ListTasks` | 读 | — | 组件间协议，不做数据权限过滤 |

**REST**（见 `contracts/workflow.openapi.yaml`，路径前缀 `/infra/workflow/**`）：

| 路径 | 权限键 | 说明 |
|---|---|---|
| `GET /tasks` | `infra.workflow.task.view` | 我的待办，owner/org 两维 OR |
| `GET /tasks/{id}` | `infra.workflow.task.view` | 详情 + 审批历史 |
| `POST /tasks/{id}/approve` | `infra.workflow.task.act` | 同意，只认当事人本人 |
| `POST /tasks/{id}/reject` | `infra.workflow.task.act` | 驳回，必须带附言 |
| `GET /admin/tasks` | `infra.workflow.admin` | 全局视图，绕过 owner 维但不绕过 org 维 |

**发布事件：** `infra.workflow.task.created.v1`/`.completed.v1`/`.cancelled.v1`（核心）、`.overdue.v1`（旁路）。
**消费事件：** 无——零消费是设计前提（§6.6 铁律三）。

详细字段与判据见设计计划 `docs/design/infra-workflow.md`——那份是真相源，这里是速查表。

## 4. 数据模型

| 表 | 分区 | 唯一约束 | 说明 |
|---|---|---|---|
| `workflow_tasks` | 不分区（有前提，见 README） | `id` 主键 | `assignee_dept_path` 是被指派人的部门，不是单据部门；`summary` 是 JSONB（内容永远是本组件自己 gRPC/HTTP 绑定产出的合法 JSON，安全，同 `infra-iam-casdoor` payload 该用 TEXT 还是 JSONB 的教训对比） |
| `workflow_task_actions` | 不分区 | `id` 主键 | 审批历史，只增不改 |
| `command_idempotency` | 不分区 | `idempotency_key` 主键 | 三个写命令统一走这张表 |

另有全组件通用的 `event_outbox`（周分区）——**没有 `event_inbox`**，本组件零消费。

**实测验证**（真跑在 `infra_workflow` schema + 真实 PostgreSQL，非 mock）：`CreateTask`/`CloseTask`/`CancelTask` 的 claim-first 幂等（同一个 `idempotency_key` 重放返回同一个结果、不重复发事件）、`ApproveTask`/`RejectTask` 对非 `PENDING` 待办统一报 `ErrNotPending`、`GetTaskStatus` 区分 `NOT_FOUND` 与 `CANCELLED`、按 `idempotency_key` 反查、`BatchGetTasks` 跳过查不到的 id、**`ListTasks` 的 OR 语义与 `AdminView` 的 toggle 语义**（回归测试专门覆盖了曾经出现过的 `ScopePrefix` 留空导致越权的那个 bug）、`GetTaskDetail` 的 `InScope` 可见性校验、`ApproveTask` 拒绝非当事人代批、超期扫描只通知一次且绝不修改 `status`、迁移连跑两次幂等、Docker 镜像自检（`/bin/sh` + `wget`）。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| `GET /tasks` 意外看到了别的部门/别人的待办 | `service.ListMyTasks`/`ListTasksAdmin` 没有把 `ScopeOwner`/`ScopePrefix` 都正确地从 `besdk.ScopeOf(ctx)` 派生——OR 语义下漏填一个会让另一个的空值在 SQL 里退化成匹配全部 | 检查 `repo.ListInput` 的 `ScopeOwner`/`ScopePrefix` 是否都来自真实的 `ScopeOf(ctx)`，不能有硬编码的空字符串默认值参与 OR |
| `ApproveTask`/`CloseTask` 对一个明明是 `PENDING` 的待办也报 `ErrNotPending` | 大概率是并发的另一个动作抢先改了状态（`FOR UPDATE` 保证了不会脏读，但两个几乎同时到达的请求里后到的那个确实应该失败），或者调用方缓存了一个过期的 `task_id`/状态快照 | 这是设计行为，不是 bug——重新 `GetTaskStatus`/`GetTaskDetail` 确认当前真实状态，不要重试同一个动作 |
| `buf lint` 报某个消息被多个 rpc 复用 | `RPC_REQUEST_RESPONSE_UNIQUE` 类规则——同一个消息类型只能给一个 rpc 当返回值 | 除了那个"读接口直接返回聚合根本身"的名额外，其余 rpc 都要包一层专属的 `XxxResponse` |
| 超期事件一直不发 | `startOverdueScan` 单次扫描失败只记日志继续，不会让循环退出（同 `partition.Start` 的既有判据），所以循环本身很难"停掉"；更可能是 `due_at` 根本没设置（未设置表示无截止时间，永远不会超期），或者 `overdue_notified_at` 已经非空（超期通知只发一次，这不是 bug） | 查日志确认 `MarkOverdueAndPublish` 有没有报错；用 `SELECT due_at, overdue_notified_at FROM workflow_tasks WHERE id = ...` 确认这条待办本该被扫到 |
