# infra/workflow 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、规则、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目：审批与统一待办在协议 09，投影在协议 02，注册表（任务类型）在协议 19，前端的动作直达所属组件在协议 20，数据范围在安全 07；决定 D19（身份保留，职责改为统一待办）、D68（待办只订阅共享任务契约、不转发动作）。流程管理方怎样产生任务在线协议第 17 章（流程内核）。首批范围是装配项目阶段计划 C7 的 P0 定的（AI 定，待复核）。

## 边界

统一待办：把各流程管理方发布的任务投影汇总起来，给每个人看“我的待办”和“已办”，并告诉前端每个任务属于哪个组件、动作发到哪里。

| 不在这里 | 归谁 |
| --- | --- |
| 审批实例、任务、分配、决定的检查与记录 | 流程管理方：业务组件里的流程内核（线协议第 17 章），或可选引擎的适配组件 |
| 用户的决定动作（同意、拒绝） | 前端直接发给任务所属的组件，本组件不转发、不保存决定、不在本地关闭任务 |
| 执行放行 | 业务组件按修订号与依据摘要核对 |
| 提醒、升级 | 流程管理方经 `infra/notification`（以后） |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 任务投影 | 流程管理方按共享任务契约发布的一个任务的完整状态；本组件按版本覆盖保存 | `task`；事件 `<领域>.<组件名>_task.changed.v1`（例 `erp.purchase_task.changed.v1`），载荷 `be.flow.task.v1` |
| 心跳 | 流程管理方有待处理或暂停的任务时每 5 分钟发的一条事实（线协议 P17.18） | `<领域>.<组件名>_task.heartbeat.v1` |
| 共享任务契约 | 任务投影的 schema，在线协议仓库 `be-protocol` 的 `schemas/flow/task.v1.schema.json`（流程内核在 SDK 里按它发布，本组件按它消费）；发布方的事件类型引用它 | — |
| 任务类型 | 注册表里全局唯一的名字（例 `erp.purchase.order.approval`），每种由部署选定一个流程管理方 | `task_type` |
| 发布方 | 部署为某任务类型选定的流程管理方组件；更换之后原来的那个是“以前的发布方”，只为它已有的任务继续发投影 | 配置键 `WORKFLOW_TASK_SOURCES`（WF08） |
| 我的待办 | 候选处理人包含我、状态待处理的任务 | — |
| 已办 | 我作出决定的任务，与我曾是候选、已结束的任务 | — |
| 动作入口 | 任务所属组件的标准路由 `POST /be/flow/tasks/{id}/decisions`（线协议 P17.14），由组件推出 | — |
| 可能不是最新 | 发布方的投影久未到达（发布方不可达或事件积压）时给任务的标注 | `stale` |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `task` | 发布方组件、任务身份、任务类型、单据引用（组件、类型、身份、单号）、摘要、候选处理人（数组）、状态、决定与处理人、截止、实例状态、法人、版本、收到的时刻（本组件收下这一版投影的时刻，答复里的 `received_at`） | 已结束的保留作历史；以后转层（协议 11） |
| `task_candidate` | 任务 × 候选处理人：现在是不是候选（随投影整体替换）与曾经是候选（只追加，已办要用） | 随任务 |
| `publisher` | 每个发布方最后一次心跳与最后一份投影的时刻（可能不是最新的判断） | 随配置 |
| `rejected_projection` | 被拒的投影：发布方、任务类型、原因、时刻（发布者核对，安全事件另写审计） | 保留 90 天 |

## 规则

| 规则 | 内容 |
| --- | --- |
| WF01 | **发布者核对**：部署配置 `WORKFLOW_TASK_SOURCES` 为每种任务类型列出现在的发布方组件，和可选的以前的发布方（协议 09 的更换流程管理方：按实例记录管理方）；本组件在启动时按配置订阅这些发布方的流上的任务投影与心跳。投影的任务类型不在配置里，发布者（信封的来源组件，消息系统按服务身份限制谁能在哪个流上发布）既不是现在的发布方，也不是对一个已有任务的以前的发布方：拒绝，记 `rejected_projection` 与一条安全审计，不改任何任务。配置的值是不是注册表里登记的任务类型与它允许的发布方，由装配的检查核对（协议 19），本组件只核对格式 |
| WF02 | **按版本覆盖**：以“发布方 + 任务身份”为键，新版本整体替换（现在的候选一起替换，曾经的候选只追加），旧版本与同版本丢弃 |
| WF03 | **我的待办**：候选处理人包含调用者、状态 `pending` 的任务，按截止（没有的按收到的时刻）排序，游标分页；可按任务类型、法人筛选。数据范围就是“候选包含我”：本组件不判断别的组件的授权，候选由发布方按它的分配与授权解析（线协议 P17.8） |
| WF04 | **已办**：决定的处理人是调用者的、已结束的任务，与调用者曾是候选的已结束任务；游标分页 |
| WF05 | **读取一个任务**：调用者现在或曾经是它的候选处理人、或是决定者，才能看，否则答 404（发起人与有单据读取权的人在所属组件里看，线协议 P17.14；本组件不判断别的组件的授权）。答复带动作入口（所属组件 + 标准路由）与 `stale` |
| WF06 | **可能不是最新**：一个发布方的最后一次心跳与最后一份投影都早于阈值（配置 `WORKFLOW_STALE_AFTER`，缺省 15 分钟，是心跳间隔的三倍），而本组件还有它的待处理任务时，这些任务标 `stale`；不改状态（不在本地关闭任务）。安静但健康的发布方照常发心跳，不会被标 |
| WF07 | **不保存决定、不转发动作**：本组件没有决定的路由；用户的动作由前端直接发给所属组件，显示只随发布方的下一份投影改变 |
| WF08 | **配置与订阅**：`WORKFLOW_TASK_SOURCES` 是逗号分隔的 `<任务类型>=<现在的发布方>[|<以前的发布方>…]`（例 `erp.purchase.order.approval=erp/purchase,erp.payment.request.approval=erp/payment`）；格式不对、一种任务类型写了两次，成员启动失败。发布方组件的流与事件类型由组件身份推出（线协议 P17.15：组件 `erp/purchase` 的流是 `erp.purchase`，投影 `erp.purchase_task.changed.v1`，心跳 `erp.purchase_task.heartbeat.v1`），每个出现在配置里的组件（现在或以前的）订阅一次；没有配置时不订阅，待办是空的 |
| WF09 | **投影的形状**：载荷按共享任务契约（`be.flow.task.v1`）核对，不合（或载荷里的组件不是信封的来源）按 `malformed` 拒绝，同 WF01；合格的投影原样保存，读取时原样答回 |

## 命令与查询

| 命令或查询 | 面 | 操作 |
| --- | --- | --- |
| 我的待办、已办、读取一个任务 | 用户面 | `infra.workflow.task.read`（授予给所有用户：范围由“候选包含我”限定） |

## 事件

不发布业务事件（只消费任务投影）。订阅：部署配置列出的发布方的 `<领域>.<组件名>_task.changed.v1` 与 `_task.heartbeat.v1`（订阅随配置在启动时建，WF08）。`component.yaml` 的 `events.subscribes` 只能写精确的类型或带结尾 `*` 的前缀，写不出“任何组件的 `_task.changed.v1`”：首批列出两个已知发布方的前缀（`erp.purchase_task.*`、`erp.payment_task.*`），新的发布方上线时只为 BrickKit 的依赖显示补一行，运行不受影响（向 BrickKit 提功能请求：后缀匹配）。

## 部署与替换

低到中负载，适合外壳。同契约的待办实现可替换。

## 验证故事

1. 在待办中点同意后超时，前端显示“处理中，结果未确认”，用同一个幂等键重试，所属组件只记一个决定；待办随下一份投影显示已决定。
2. 所属组件不可达时，待办照常显示投影中的任务，标明可能不是最新。
3. 新业务组件上线，按共享任务契约发布任务、部署配置列出它，不需要改动或重新发布待办。
4. 伪造的投影（不是部署选定的发布方发的）进不了待办。
